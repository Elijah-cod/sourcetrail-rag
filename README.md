# sourcetrail-rag
Multi-source RAG knowledge base with hybrid search (pgvector + full-text), RRF fusion, cross-encoder reranking, and verifiable citations.

## Project layout

- `backend/` — FastAPI service (Python, uv)
- `frontend/` — chat UI
- `docs/` — design spec and architecture diagram
- `docker-compose.yml` — local Postgres + pgvector

## Local development (backend)

Requirements: [uv](https://docs.astral.sh/uv/) and Docker.

```bash
docker compose up -d db          # Postgres 17 + pgvector on localhost:5432 (run from repo root)
cd backend
cp .env.example .env
uv sync                          # create .venv and install dependencies
uv run python -m app.migrate     # create/update database tables
uv run uvicorn app.main:app --reload
# open http://localhost:8000/health  and  http://localhost:8000/docs
uv run pytest                    # run tests (Postgres and model tests skip if unavailable)
uv run pytest -m "not integration"   # just the fast tests that need no services
```

Design spec: [docs/superpowers/specs/2026-10-02-sourcetrail-rag-design.md](docs/superpowers/specs/2026-10-02-sourcetrail-rag-design.md)
UI rules (colour tokens, type, touch targets, accessibility): [DESIGN.md](DESIGN.md)

## Choosing an LLM model

Answers are generated by any OpenAI-compatible chat API (Groq's free tier by default).
Put your key in `backend/.env` as `LLM_API_KEY=...`. To see which models your key can use:

```bash
cd backend
curl -s https://api.groq.com/openai/v1/models \
  -H "Authorization: Bearer $(grep '^LLM_API_KEY=' .env | cut -d= -f2)" \
  | python3 -c "import json,sys; [print(m['id']) for m in json.load(sys.stdin)['data']]"
```

Then set `LLM_MODEL=<id>` in `.env` if you want something other than the default.

## Demo collection and evaluation

The demo collection (`backend/demo/sources/`, see `demo/SOURCES.md` for licences) mixes
Markdown docs, a PDF and a CSV. Load it into the shared demo workspace, then evaluate:

```bash
cd backend
uv run python -m app.seed_demo     # (re)load the demo collection
uv run python -m eval.run_eval     # compare vector / keyword / hybrid / hybrid + reranker
```

Results are written to `backend/eval/results.md`.

### Regression benchmark

The fixtures from the October 2026 regression reports (PDF, DOCX, Markdown, Latin-1 TXT, CSV,
HTML) with their questions and expected results live in `backend/eval/regression/`. Like the
live app, they are indexed together into one temporary workspace, searched alongside the demo
collection, and removed afterwards:

```bash
cd backend
uv run python -m eval.regression.run_regression            # ingestion + retrieval coverage, no LLM calls
uv run python -m eval.regression.run_regression --answers  # also grades the LLM's answers (uses quota)
```

Results are written to `backend/eval/regression/results.md`. To rebuild the fixtures:
`uv run --with reportlab python -m eval.regression.make_fixtures`.

The app's **Benchmarks** page shows the latest results of both scripts (they also write
`results.json` next to `results.md`).

## Continuous integration

`.github/workflows/ci.yml` runs on every push and pull request, as three jobs:

- **unit**: the backend tests that need no services (`pytest -m "not integration"`);
- **integration**: the tests that use Postgres or the real models (`pytest -m integration`),
  against a pgvector Postgres with the models cached between runs. It sets
  `REQUIRE_SERVICES=1`, which turns a skipped integration test into a failure, so a missing
  database or model can't pass as "skipped";
- **frontend**: lint and the static build.

A test is an integration test when it uses the `db`, `embedder` or `real_reranker` fixture,
or is marked `@pytest.mark.integration` (see `backend/tests/conftest.py`).

## Deployment

The `Dockerfile` at the repository root builds one image: the static frontend, the backend,
and both models baked in. At start it applies new migrations, re-indexes the demo collection
if its files changed, then serves on `$PORT` (default 8000). It needs about 400–500 MB of
memory and a full CPU or more for comfortable answer times; Render's free plan (512 MB,
0.1 CPU) is too small.

**Database: Neon (free).** Create a project, then copy its connection string (with
`?sslmode=require`). The migrations enable `pgvector` themselves.

**App: Google Cloud Run (free tier).** Cloud Run's monthly free allowance (180,000
vCPU-seconds, 360,000 GiB-seconds, 2 million requests) covers a demo: with request-based
billing, an idle app scales to zero and costs nothing. It needs a billing account (a card).

1. In the Google Cloud console, create a project and link a billing account. Add a small
   budget alert under Billing > Budgets & alerts.
2. Cloud Run > Create service > **Continuously deploy from a repository** > Set up with Cloud
   Build. Connect GitHub, pick this repository, branch `^main$`, build type **Dockerfile**
   (`/Dockerfile`).
3. Region `us-central1` (or another Tier 1 region near your Neon database), **Allow public
   access**, billing **Request-based**, minimum instances 0, maximum instances 1.
4. Container: port 8080, memory 1 GiB, 1 CPU, startup CPU boost on. Add the variables
   `DATABASE_URL` (Neon), `LLM_API_KEY` (Groq), `COOKIE_SECURE=true` and
   `TRUST_FORWARDED_FOR=true` (Google's front end appends the real client address).

Every push to `main` is then built and deployed by Cloud Build; open the `https://…run.app`
address Cloud Run shows. The first visit after the app has been idle waits while it starts
and loads the models. Stored images past Artifact Registry's free 0.5 GB cost about $0.10
per GB a month, so delete old ones now and then.

**Alternative: Hugging Face Spaces.** Docker Spaces now need a PRO plan. With one, create a
Docker Space, add the same four settings in its settings, then add the GitHub secret
`HF_TOKEN` and variable `HF_SPACE`: `.github/workflows/deploy.yml` deploys every push to
`main` that passes CI (it does nothing while `HF_SPACE` is unset). Open the app at
`https://your-name-space-name.hf.space`, not inside the huggingface.co page, where browsers
block the workspace cookie.
